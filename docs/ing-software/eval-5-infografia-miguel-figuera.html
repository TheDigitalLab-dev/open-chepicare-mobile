Implementación y Mantenimiento del producto final de software

El software no termina cuando compila: se entrega, se pone en producción y vive años evolucionando. Aquí está el mapa completo de esa última — y más larga — etapa del ciclo de vida.

01
De la construcción a la operación

¿Qué es la implementación (implantación)?

Es la fase en la que el sistema, ya construido y verificado, se instala en su ambiente real de operación y se pone a disposición de los usuarios finales. Marca la transición del proyecto: el producto deja de ser un artefacto del equipo de desarrollo y pasa a ser una herramienta de trabajo de la organización.

Una implantación mal planificada puede hacer fracasar un sistema técnicamente perfecto: la resistencia al cambio, los datos mal migrados y la falta de capacitación destruyen la confianza del usuario en el primer contacto.

Riesgo

El sistema anterior se apaga y el nuevo arranca de inmediato. Rápida y económica, pero sin red de seguridad: si el nuevo falla, la operación se detiene.

Anterior
Nuevo
Riesgo

Ambos sistemas operan a la vez durante un período y se comparan resultados. Máxima seguridad, pero duplica el trabajo y el costo de operación.

El nuevo sistema se prueba primero en un área o sede limitada; validado el piloto, se extiende al resto de la organización con las lecciones aprendidas.

03 · El dato que cambia la perspectiva

El mantenimiento domina el costo del ciclo de vida

≈ 30 %Desarrollo inicial
≈ 70 %Mantenimiento y evolución

Diversos estudios estiman que entre el 60 % y el 80 % del costo total de un sistema se consume después de su entrega (Sommerville, 2011; Pressman, 2010). Diseñar pensando en la mantenibilidad — código limpio, pruebas automatizadas, documentación de decisiones — es la inversión más rentable de todo el proyecto.

04
ISO/IEC 14764 · Norma internacional del mantenimiento

Los cuatro tipos de mantenimiento

≈ 21 %

Correctivo

Repara defectos detectados en operación: fallas de lógica, errores de cálculo, caídas del sistema.

Ejemplo · Un pago registrado no aparece en el historial del cliente.

≈ 25 %

Adaptativo

Ajusta el software a cambios del entorno: nuevo sistema operativo, nueva versión del API, nuevas leyes.

Ejemplo · Migrar la app a una nueva versión de Android o del SDK.

≈ 50 %

Perfectivo

Mejora funciones existentes o añade nuevas a petición del usuario; incluye mejoras de rendimiento.

Ejemplo · Agregar recordatorios automáticos de vacunación.

≈ 4 %

Preventivo

Reestructura y refactoriza para facilitar el mantenimiento futuro antes de que los defectos aparezcan.

Ejemplo · Refactorizar listas a componentes virtualizados.

Distribución típica del esfuerzo según los estudios clásicos de Lientz y Swanson, citados por Pressman (2010).

05
Nada se toca sin control de cambios

El proceso de mantenimiento, paso a paso

1Solicitud de cambioUsuarios o soporte reportan defectos o piden mejoras (tickets, incidencias).
2Análisis de impactoSe evalúa qué módulos, datos y usuarios afecta; se estima costo y riesgo.
3PriorizaciónEl comité de cambios aprueba, pospone o rechaza; lo urgente entra como corrección.
4ImplementaciónSe modifica el código con control de versiones y revisión por pares.
5Pruebas de regresiónSe verifica el cambio y que nada de lo que funcionaba se haya roto.
6LiberaciónNueva versión numerada, notas de cambio y despliegue a los usuarios.
06
Por qué el software nunca está “terminado”

Leyes de la evolución del software (Lehman)

I
Cambio continuoUn sistema que se usa en el mundo real debe adaptarse continuamente o se vuelve progresivamente menos útil.
II
Complejidad crecienteAl evolucionar, la estructura del sistema se degrada y su complejidad aumenta, salvo que se trabaje activamente para reducirla.
VI
Crecimiento continuoLa funcionalidad debe crecer a lo largo de la vida del sistema para mantener satisfechos a sus usuarios.
VII
Calidad decrecienteLa calidad percibida decae si el sistema no se adapta con rigor a los cambios de su entorno operativo.
Caso de estudio real · proyecto de la unidad curricular

Cómo lo aplica Chepicare 🐾

La aplicación móvil de atención veterinaria a domicilio del consultorio Chepicare (Expo SDK 56 · React Native · TypeScript, sobre un backend API REST de 157 rutas) ya practica la implantación y el mantenimiento disciplinados:

🚦 Implantación por fasesEl producto se entrega en incrementos por dominio — público, dueño y administrador — validados con la clienta en cada revisión de sprint.
🧪 Regresión real, no simulada15 suites con 49 pruebas de integración corren contra el backend real antes de cada commit: la red de seguridad del mantenimiento.
🔀 Control de cambiosRamas cortas, pull requests con revisión y commits convencionales: cada cambio queda trazado desde la solicitud hasta la liberación.
🛡️ Compuertas automáticasPruebas, tipos, lint y react-doctor bloquean el push de código defectuoso: mantenimiento preventivo integrado al proceso.
📱 Despliegue móvilBuilds versionados con Expo y actualizaciones controladas: liberar una corrección no exige reinstalar la aplicación completa.
📖 Memoria de decisionesLos ADR (registros de decisión arquitectónica) documentan el porqué de cada diseño, reduciendo el costo de entender el sistema en el futuro.
